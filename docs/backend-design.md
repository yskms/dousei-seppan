# 同棲折半：バックエンド設計メモ

- 更新日：2026-11-20
- 状態：設計方針まとめ／実装前レビュー用
- バックエンド候補：Cloudflare Workers + D1（SQLite）
- 仕様の正本は企画メモ（[plan.md](plan.md)）。このメモは、それをD1とWorkerでどう実現するかをまとめる。食い違ったときは企画メモに合わせる
- 認証：Singfolioの実装（`singfolio/worker`）をこのリポジトリの `worker/` にコピーして使う。アカウントはSingfolioと共通にせず、アプリごとに分ける

---

## 1. 方針

### アプリの前提

- 2人での利用を中心に、3人以上のグループにも対応する。
- 家計の共通支出を記録・集計するアプリ。旅行の異通貨割り勘アプリではない。
- 1グループにつき1通貨。グループ内で複数通貨を混在させない。通貨換算・為替レート取得は対象外。
- 月単位で集計する（1日〜末日が基本）。月は、月の途中でも締められる（途中で精算して解散したい、月末を待たずに締めたい、など）。
- 支出の日付と、どの月に登録するかは独立させる。締めた後に出た支出（入力漏れや、早めに締めた月の残り）は、登録できる月に登録する（8章）。
- 月締め後、その月の支出は追加・編集・削除できない。締めの取り消し・再オープン機能は設けない。
- 前の月の締めと、その月のすべての送金の精算または繰越が済んでいないと、次の月は締められない。
- 締めた月の送金ごとに、「精算する」か「次月に繰り越す」を選ぶ。月やグループ全体をモードで固定しない。
- 繰り越した送金は、翌月を締めるときに、メンバーごとの差額に足してから送金を作り直す（4章）。翌月の支出・負担額には加算しない。もう一度繰り越せば、さらに翌月に合算されるだけなので、「再繰越」という操作は無い。
- 費目による負担は、月の費目ごとの合計に負担割合をかけて計算する。月の途中で割合を変えたら、その月全体に反映する。締めた時点で確定する。
- 固定費はテンプレートとして登録し、毎月の支出レコードは通常の支出として作成する。
- 招待URLはワンタイム・発行から3日で失効。URLを開いただけでは参加させず、グループ名と招待元を表示して「参加する」を押した後に参加処理を行う。
- 新規メンバーが閲覧できる履歴は参加月以降。脱退は月単位（「今月で脱退する」のみ）で、脱退する月を締めた時点か、翌月1日の早いほうで確定する。
- ローカル銀行連携、レシートOCR、個人資産管理などは対象外。

### インフラ方針

- Cloudflare Workers + D1を第一候補としてプロトタイプを進める。
- SingfolioのApple / Google認証・セッション処理を、`worker/` にコピーして使う。リポジトリが別なので、共通のパッケージにはしない。データ領域・設定・クライアントIDは、アプリごとに分ける。
- コピーしたときは、コピー元のSingfolioのコミットを `worker/` のコードコメントに書く。Singfolio側で認証を直したときは、その差分を手で取り込む。
- Honoなど、既存プロジェクトで使っていない仕組みを理由なく追加しない。
- 開発中はFree枠で検証し、公開時にWorkers Paid（月額5 USDを目安）へ移行する案。
- D1はWorkerからのみアクセスさせ、クライアントから直接アクセスさせない。
- Durable Objects、シャーディング、読み取りレプリカ等は初期段階では導入しない。
- 月初の処理（脱退の確定など）と固定費の自動登録は、Cron Triggersで行う（7章）。

## 2. 金額・通貨・割合

### 金額

金額は浮動小数点ではなく、通貨の最小単位を整数で保存する。

| 通貨 | 表示例 | DB保存値 | 小数桁 |
|---|---:|---:|---:|
| JPY | 1,234円 | 1234 | 0 |
| USD | $12.34 | 1234 | 2 |
| EUR | €12.34 | 1234 | 2 |
| KWD | 12.345 KWD | 12345 | 3 |

- `expense_groups.currency_code` にISO 4217の3文字コードを保存する。
- `expense_groups.currency_minor_unit` にその通貨の小数桁数を保存する。
- 通貨マスター（通貨コードと小数桁数の対応表）はアプリ側で管理する。最初のリリースから、主要通貨を選べるようにする。初期の一覧の案は JPY・USD・EUR・GBP・AUD・CAD・CNY・KRW。要望があれば追加する。
- グループ作成時の初期値はJPY。
- グループ作成後、支出が1件でも登録されたら通貨変更不可。
- 月締めにも通貨コードと小数桁数をスナップショット保存する。
- 1件の金額の上限は `10^12`（JPYで1兆円）。APIで検証し、DDLにもCHECKを置く。
- 割合をかける掛け算は、BigIntで行う（`worker/src/settlement.ts`）。`10^12` に割合（最大10000）をかけると、JavaScriptの安全整数（2^53 - 1）を超えるため。月の合計や負担額そのものは安全整数に収まる前提で、超えたら計算を止める（エラー）。

### 負担割合

割合は1万分率（basis points）で整数保存する。

| 表示 | DB値 |
|---:|---:|
| 100% | 10000 |
| 60% | 6000 |
| 50% | 5000 |
| 40% | 4000 |
| 33.33% | 3333 |

- 負担対象メンバー間の割合合計は10000。
- 画面上は通常のパーセント表示にする。
- 0.01%単位まで指定可能な設計。UIでそこまで細かい指定を見せるかは別途判断する。

### 金額指定

- メンバーごとの指定額合計は支出総額と完全一致必須。
- 差額の自動配分はしない。合計不一致なら登録できない。

### 端数

- 均等割り・割合割りでは、最小通貨単位で計算する。
- 各メンバーの値を切り捨てで出し、残った端数を、割合が0より大きいメンバーに固定順で1単位ずつ配分する。
- 例：10,000円を3人で均等割り → 3,334円、3,333円、3,333円。
- 1円単位の公平性を追求する機能は設けない。ただし各メンバーの負担額の合計は、元の金額と必ず一致させる（一致しないと、精算の差額の合計がゼロにならない）。
- 固定順はメンバーIDなど、端末やリクエスト順に依存しない値を使う。
- 費目による負担では「費目の月合計」に対して、個別設定の支出では「その支出の金額」に対して、この端数処理を行う。

## 3. 負担・精算ロジック

### 負担方法

支出ごとに `split_method` を持つ。

- `category`：費目の負担割合を使う（既定）。負担額は支出ごとには保存せず、月の集計で計算する。
- `equal`：対象メンバーで均等割り。
- `ratio`：支出ごとに指定した割合で割る。割合合計は10000。
- `fixed`：支出ごとに金額を指定。指定額合計は支出額と一致。
- `single`：1人が全額負担する。

`category` 以外は、企画メモの「この支出だけ負担割合を変える」にあたる。支払った人（payer）と負担する人は別概念として保存する。支払った人が全額負担するとは限らない。

### 保存する負担データ

- `expenses.amount_minor`：支出総額
- `category_month_settings`：月ごと・費目ごとの設定（上限額つきの負担の、負担する人と上限額）
- `category_month_shares`：月ごと・費目ごと・メンバーごとの負担割合
- `expense_allocations`：`category` 以外の支出の、メンバーごとの確定負担額（`burden_minor`）。割合指定のときは `share_basis_points` も残す

`category` の支出には `expense_allocations` を作らない。割合を変えたときに、その月の支出を計算し直す必要をなくすため。個別設定の支出は、登録時に計算した負担額を保存し、あとから計算ロジックが変わっても変化しないようにする。

### 月ごとの負担割合

- ある費目・ある月の設定は、`category_month_settings` のうち、その月以前で最も新しい月の行と、同じ月の `category_month_shares` の行の組を使う（行が無い月は、直前の月の設定を引き継ぐ）。
- `category_month_settings` の1行と `category_month_shares` の行の組は、常に同じ月でまとめて書く。どの月の設定を使うかは、`category_month_settings` の月で決まる。
- 読み取り時には行をコピーしない。次のときに、その月の行の組を書く。
  - その月の割合を変更したとき
  - 費目を作ったとき（有効なメンバーで均等）
  - メンバーが参加した月（その月の全費目を、新しいメンバーを含めた均等にリセットする）
  - 脱退が確定した月（その月の全費目を、残るメンバーでの均等にリセットする）
  - 月締め時（その月の行が無ければ、引き継いだ割合を書き、確定値として残す）。アーカイブした費目は、その月に支出がなければ書かない（使わない行が毎月増え続けるため。設定は、引き継ぐ元の行がそのまま使われる）
- 1つの費目・月の行は、その月に負担対象となる全メンバーの組として書き、合計を10000にする。
- 割合を変更できるのは、締めていない月だけ。
- メンバーの増減で均等にリセットするときは、上限額の設定も外す（`cap_member_id`・`cap_minor` をNULLにする）。

### 上限額つきの負担

`category_month_settings` に `cap_member_id`（負担する人）と `cap_minor`（上限額）があるとき、その費目の `category` の支出の月合計 `T` を次のように分ける。

1. 負担する人が `min(T, cap_minor)` を負担する。
2. 超えた分 `T - cap_minor`（0より大きいとき）を、`category_month_shares` の割合で全員に分ける（端数処理は2章）。負担する人の割合は、上限額を設定したときの既定値を0にする（変更できる）。

- 例：2人、外食の上限が自分の10,000円、超えた分の割合が自分0%・相手100%。`T` が8,000円なら、自分8,000円・相手0円。`T` が15,000円なら、自分10,000円・相手5,000円。
- 上限額は費目の月合計に対してかける。支出ごとの個別設定（`category` 以外）の支出は、`T` に含めない。
- 負担する人は、その月の `category_month_shares` に含まれるメンバーでなければならない（割合は0%でよい）。

### 月次集計

メンバーごとに次を集計する。

- 支払額：そのメンバーが支払った支出の合計
- 負担額：次の合計
  - 費目ごとに、`category` の支出の月合計 × その月の割合（端数処理は2章。上限額つきの費目は前節のとおり）
  - `category` 以外の支出の `expense_allocations.burden_minor`
- 差額：支払額 - 負担額
- 繰越：前の月の締めで `carried` にした送金の合計。送金先なら足し、送金元なら引く（4章）
- 精算する額：差額 + 繰越

精算する額がプラスなら受取側、マイナスなら支払側、ゼロなら精算不要。全員の差額の合計も、繰越の合計も、必ずゼロになる。

支出の総額・負担額・差額は、その月の支出だけから出す。繰越は精算する額にだけ入れる。

### 精算先の組み合わせ

「精算する額」をもとに、支払側と受取側をそれぞれ固定順で並べ、先頭同士から少ない方の残額を精算額として組み合わせる。残額がゼロになった側を次のメンバーに進める。全員の残額がゼロになるまで繰り返す。

- 繰越を足した後の額から作り直すため、繰り越した送金の組み合わせ（誰から誰へ）は、翌月には残らないことがある。たとえば「A → B」の繰越が、新しいメンバーCを経由して「A → C」「C → B」になることもある。各メンバーが払う・受け取る合計額は正しいので、これでよいとする。

- 3人以上でも同じアルゴリズムを使う。送金は最大で「差額がゼロでないメンバー数 - 1」件になる。件数が最少になることまでは保証しない（企画メモの「件数が少なくなるように」は、この意味とする）。
- 精算結果は `settlement_transfers` に保存し、後から再計算して過去の送金先・金額が変わらないようにする。

## 4. 月締め・精算・繰越

### 月締めの条件

Workerで次をすべて確認してから締める。

- 対象月が、カレンダー上の今月以前（グループのタイムゾーン）。月の途中でも締められるが、まだ始まっていない月は締められない。
- 対象月がまだ締められていない。
- 前の月が締め済みで、その送金がすべて `settled` または `carried`。グループで最初の月（最初の支出がある月、または作成月）はこの条件を問わない。
  - 「最初の月」は、締めがまだ1つも無いときの、最初の支出がある月以前の月（支出が1件も無ければ作成月以前）。作成月に支出が無く、翌月に最初の支出を登録したグループは、作成月を締めずに、翌月を最初に締められる。それより前の月に支出を登録すれば、そちらが最初の月になる。
  - 締めが1つでもあるとき、前の月が未締めなら締められない。飛ばした月も、古い月から順に締める。
  - 最後に締めた月より前で、締めていない月（飛ばした月）は、締められない（`month_skipped`）。締めた月は `month_closed`。古い月を後から締めると、翌月の締めに繰越を足す前提が崩れるため。
- 操作者が、その月に有効なメンバー（参加（復帰）した月から、脱退月まで。5章）。

### 月締めの処理

1. 対象月の支出・個別負担額・費目の割合と、前の月の締めの `carried` の送金を取得
2. メンバーごとの支払額・負担額・差額・繰越・精算する額を計算
3. 送金元・送金先・金額の組み合わせを計算
4. 1回の `batch()` で次を書く（8章の競合制御つき）
   - 行が無い費目の `category_month_settings`・`category_month_shares`（引き継いだ設定を書き、確定値として残す）
   - `monthly_closings`
   - `closing_member_summaries`
   - `closing_category_burdens`（費目ごとの合計と、メンバーごとの負担額。履歴画面の内訳用）
   - `settlement_transfers`
   - この月を脱退月に選んでいるメンバーの脱退の確定（5章の2。`worker/src/membership.ts` の `confirmLeaveStatements`）。そのメンバーが、グループの最後の1人のときは、締めずにグループを削除する（5章）
   - 脱退が確定した（`leaving`）メンバーのうち、脱退月が締められ、関わる送金に未処理が無く、繰越先の月が未締めの繰越も無いメンバーを `left` にする（5章の4。送金が0件なら、ここで脱退済みになる）

月締め後は、API側で対象月への支出の追加・編集・削除と、割合の変更を拒否する。UIだけで制限しない。

送金が0件の月（全員の差額がゼロ）は、締めた時点で処理済みとなる。

### 精算と繰越

送金ごとに状態を持つ。

- `pending`：未処理
- `settled`：精算済み
- `carried`：次月に繰越済み

- 許可する状態遷移は `pending → settled` と `pending → carried` だけ。どちらも、確定後に戻せない。
- 脱退を選んだメンバー（`leave_requested_month` あり）、`leaving`、`deleted` のメンバー（5章）が送金元・送金先のどちらかである送金は、`carried` にできず、`settled` にするしかない。削除されたユーザーとの送金も、金額と方向は表示されているので、残るメンバーが確認して精算済みにする。
- 月は、すべての送金が `settled` または `carried` になった時点で処理済みとなる。処理済みかどうかは送金の状態から判定し、別に保存しない。

### 繰越

- 繰越先は常に、締めた月の翌月。翌月を締めるとき、前の月の締めの `carried` の送金を、メンバーごとの繰越として精算する額に足す（3章）。
- 繰越の元は、元の送金レコード（`status = 'carried'`）。締める前の見込みの計算でも、同じレコードから足す。締めた結果は `closing_member_summaries.carried_in_minor` に残す。
- 前の月の送金がすべて処理済みでないと翌月は締められないため、翌月を締める時点で繰越の額は確定している。
- 繰越を何度選んでも、毎月「前の月の締めの `carried`」だけを足すので、同じ金額を二重に数えない（2か月前の繰越は、前の月の送金にすでに入っている）。
- 繰越分は、翌月の支出の総額・負担額には含めない。
- 繰越を含むことは、繰越先の月を閲覧できる全メンバー（その月に参加した新メンバーを含む）に見せる。

## 5. メンバーの参加・脱退・匿名化

### メンバーの状態

| `status` | 意味 |
|---|---|
| `active` | 参加中。`leave_requested_month` が入っていれば「今月で脱退する」を選んだ状態で、脱退が確定するまで取り消せる |
| `leaving` | 脱退が確定した（脱退月を締めた、または翌月1日を過ぎた）が、関わる送金が未処理のため、メンバーとして残っている |
| `left` | 脱退済み。名前は残す。グループのデータは見られない |
| `deleted` | アカウント削除済み。名前は匿名化する。削除した月までは、「削除されたユーザー」として集計に含める |

### 参加

- 招待URLを開いただけでは参加しない。招待内容の確認もログイン後に行う。
- 招待情報としてグループ名・招待元を表示する。
- ユーザーが「参加する」を押した時点で、トークン・期限・未使用・未取消を検証して参加処理する。
- 招待トークンは平文で保存せず、ハッシュを保存する。招待はワンタイム、期限は3日。
- 参加処理はグループへの書き込みとして `data_version` を上げる（8章）。同じ招待で同時に参加しようとしても、片方は409になる。
- 新規メンバーの `history_from_month` は参加月とする。
- 参加月の全費目の割合を、新しいメンバーを含めた均等にリセットし、見直しのアラートを出す。
- `category` 以外の負担方法の固定費は、自動登録を止め（`paused_reason = 'member_changed'`）、アラートを出す。
- 一度脱退した人（`left`）が再参加する場合は、元のメンバー行を `active` に戻す。`history_from_month` は復帰した月にし、`leave_requested_month`・`expense_end_month`・`left_at` を消す。
- 参加月がすでに締められているとき（今月を早めに締めた後）は、締めた月の割合には触れず、**翌月**の全費目の割合をリセットする。`history_from_month` は、参加月（締めた月）のまま。
- 表示名は、参加するときに入力する（必須）。色は、サーバーが、他の参加中のメンバーと重ならないように選ぶ（9章の色の一覧）。復帰する人は、元の色が使われていなければ、そのまま。
- リセットする全費目には、アーカイブ済みの費目も含める（あとで戻した費目が、古い割合に戻らないように）。固定費は、すでに止まっているもの（手動の停止など）の理由を上書きしない。

### 招待の取り消し

- 発行した人は、未使用の招待をいつでも取り消せる（`revoked_at`）。
- 発行した人の脱退が確定したとき、またはアカウントを削除したときは、その人が発行した未使用の招待をすべて取り消す。
- `leaving` 以降のメンバーは招待を発行できない。

### 脱退

1. 「今月で脱退する」：`leave_requested_month` にカレンダー上の今月（脱退月）を入れる。確定するまでは取り消せる（値を消す）。最後の1人の場合は、グループのデータが完全に削除され元に戻せないことを確認ダイアログで示す。
2. 脱退の確定：脱退月を締めたとき（締めのbatchの中で）、または翌月1日（月初のCron、7章）の早いほう。脱退を選んだ時点で脱退月がすでに締められていれば（早めに締めた後）、その場で確定する。確定時に行うこと：
   - `expense_end_month` に脱退月を入れ、`status` を `leaving` にする。翌月以降の支出の支払者・負担者にできない。
   - 残るメンバーで、翌月の全費目の割合を均等にリセットし、アラートを出す。その翌月がすでに締められている、またはいま締める月のとき（脱退月が、最初の締めで飛ばされた月のとき）は、締めた月の割合は確定しているので、リセットしない。
   - 発行した未使用の招待を取り消す。
   - 脱退者が支払者の固定費のうち、付け替えられていないものは自動登録を止める（`paused_reason = 'payer_left'`）。付け替えのアラートは、脱退を選んだ時点から出す。
   - `category` 以外の負担方法の固定費は、自動登録を止める（`paused_reason = 'member_changed'`）。脱退者が支払者の固定費は、先に `payer_left` で止まっているので、理由は `payer_left` のまま。すでに止まっているものの理由は、上書きしない。
   - 最後の1人だった場合は、グループを削除する（後述）。
     - 「最後の1人」は、参加中・脱退が確定した（`leaving`）メンバーが、抜ける1人だけのとき（`worker/src/membership.ts` の `isLastMember`）。2人以上が同時に抜けるときは、お互いの精算が残るので、グループは消さない（全員が脱退済みになったグループの後片付けは、12章）。
     - 月締めで確定するときは、その月を締めずにグループを削除し、200 `{ "groupDeleted": true }` を返す（9章）。脱退を選んだ時点で脱退月が締め済みなら、その応答で同じく `groupDeleted` を返す。
3. `leaving` の間も、集計・締め・精算には通常どおり参加し、グループのデータを見られる。
4. 脱退月が締められ、その人が関わる送金がすべて `settled` になったら `left` にする（送金が0件なら、締めた時点で `left`）。この遷移は、締めと精算の処理の中で行う。
   - `carried` の送金は、繰越先の月（締めた月の翌月）を締めるまで、未処理と同じに扱う。繰り越した額は、翌月を締めるまでどの送金にも入っていない。そのあいだに `left` にすると、翌月の締めでその人が関わる送金ができても、本人は見られず、精算できない。繰越先の月を締めると、繰越は翌月の送金に作り直され、その送金を `settled` にすれば `left` になる（`leaving` のメンバーは、脱退月より後の月も見られる）。
   - 繰り越したあとで、その人が脱退を選ぶこともある（締めた月のうちに脱退を選ぶと、その場で確定する）。脱退を選ぶ操作は、繰越が残っていても断らない。上の規則で、`left` にならずに待つだけ。
   - 繰り越した額の送金（翌月の送金）は、本人が脱退を選んでいるので、さらに繰り越せず、`settled` にする（4章）。

月の途中で抜けたいときは、脱退を選んでから、その月をすぐに締めて精算すればよい。その月の残りの支出は翌月分として登録し、翌月の通常の支出とあわせて、残るメンバーの新しい割合（均等リセット後）で計算する。

- **Cronが確定させるまでの間も、APIは、脱退月（`leave_requested_month`）が終わったメンバーを確定したものとして扱う。** 翌月1日のCronは1時間ごとで、競合すれば次の回に回るため、`status` が `active` のままの時間がある。その間も、本人は支出を記録できず（`worker/src/access.ts` の `canWriteExpenses`）、他のメンバーも、本人を翌月以降の支払者・負担の対象にできない（`worker/src/expenses.ts` の `isMemberAvailable`）。待つと、あとで確定しても戻らない個別の負担額が、翌月の支出に残る。脱退の取り消しは当月中だけ（9章）なので、脱退月が終わったあとに取り消されることはない。
- 他のメンバーを外す機能は設けない。
- 過去の支出・負担・精算履歴は削除しない。脱退後のメンバー行は履歴・精算参照のため残し、名前もそのまま表示する（「脱退済み」と併記）。
- 2人グループで1人が脱退した場合は、残った1人のグループとして存続する。

### グループの削除

最後の1人が脱退したとき、またはアカウントを削除したときに、そのグループのデータをすべて物理削除する。外部キーに `ON DELETE CASCADE` を付けていないため、1回の `batch()` で子から順に消す。

`settlement_transfers` → `closing_category_burdens` → `closing_member_summaries` → `monthly_closings` → `expense_allocations` → `expenses` → `recurring_expense_runs` → `recurring_expense_allocations` → `recurring_expenses` → `category_month_shares` → `category_month_settings` → `categories` → `invites` → `group_members` → `expense_groups`

### アカウント削除

- 認証はSingfolioの `POST /auth/delete` に揃える。セッションに加えて再認証を求め、その場で得たAppleの認可コードでrevokeする。リフレッシュトークンはD1に保存しない。
- 月単位の脱退の規則によらず、すべてのグループからすぐに抜ける。1回の `batch()` で次を行う。
  - 自分が最後の1人のグループを削除する（上記）。
  - 残りのグループで、自分のメンバー行（過去に脱退したものを含む）を `status = 'deleted'`、`display_name = '削除されたユーザー'`、`user_id = NULL` にする。参加中だったグループでは、`expense_end_month` をカレンダー上の今月にし、翌月の全費目の割合を残るメンバーでの均等にリセットする。
  - 削除した月までの、締めていない月の集計には、「削除されたユーザー」として含めたまま計算する（費目の割合・個別負担はそのまま）。削除後に登録する支出の支払者・個別負担の対象には選べない。費目の割合から外したいときは、残るメンバーが0%にする。
  - `closing_member_summaries.display_name_snapshot` も同じ表現に匿名化する。
  - 自分が発行した未使用の招待を取り消す。
  - 自分が支払者の固定費は自動登録を止め（`paused_reason = 'payer_left'`）、付け替えのアラートを出す。
  - 関わるグループすべての `data_version` を上げる。
  - 最後に `users` の行を消す。`identities`・`sessions` は `ON DELETE CASCADE` で消える。
- 実装は `worker/src/accountDeletion.ts` の `deleteAccount`（競合制御は8章の `writeToGroups`）。`POST /auth/delete`（再認証・Appleのrevoke）は未実装で、それが再認証のあとに呼ぶ（12章）。グループごとの扱いは次のとおり。
  - 「自分が最後の1人」は、自分以外に、参加中・脱退が確定した（`leaving`）メンバーがいないグループ。自分が脱退済みでも同じ（誰も見られないグループを残さない）。
  - 脱退が確定した（`leaving`）・脱退済み（`left`）のグループは、確定のときに、割合のリセット・招待の取り消し・固定費の停止を済ませているので、匿名化だけを行う（`expense_end_month`・`left_at` もそのまま）。
  - 参加中（`active`）だったグループの `expense_end_month` は、今月。ただし、脱退を選んだ月が今月より前なら（Cronが確定させる前）、その月。翌月の割合のリセットは、その翌月が未締めのときだけ（脱退の確定と同じ）。
  - 固定費は、自分が支払者のものを `payer_left`、`category` 以外のものを `member_changed` で止める（企画メモの「メンバーの増減時」に合わせた。脱退と同じ）。
- 匿名化は外部キーの `ON DELETE SET NULL` に任せず、Workerが `users` を消す前に明示的に行う。`group_members.user_id` の `ON DELETE SET NULL` は、消し漏れに対する保険。
- 金額・支出・精算履歴は残す。支出の内容（自由入力）も消さない。グループで共有している記録で、他のメンバーが代わりに入力したものも混ざるため。名前は匿名化し、内容は残すことをプライバシーポリシーに書く。

**注意：** 脱退とアカウント削除は同じ操作ではない。脱退はグループ単位で月単位、アカウント削除は全グループにすぐ及び、本人情報も消す。

### DB制約とWorker検証の分担

DBで保証するもの：

- 主キー・外部キー
- 同じグループ内の関連付け（複合外部キー）
- 金額が負数にならないこと、上限を超えないこと
- 割合が0〜10000の範囲であること
- 月・日付の書式（`YYYY-MM`、`YYYY-MM-DD`）
- 送金の状態と、精算・繰越日時の整合
- 1グループ・1か月につき締めは1件だけ
- 1支出・1メンバーにつき負担レコードは1件だけ
- 1つの固定費テンプレート・対象月につき生成記録は1件だけ

Workerで保証するもの：

- 負担割合の合計が10000
- 金額指定の合計・負担額の合計が支出額と一致
- メンバーが対象月に有効であること
- 対象月が締め済みでないこと、締めの条件（4章）
- 送金の状態遷移と、脱退者の送金を繰り越さないこと
- グループ通貨が支出登録後に変更されないこと
- 操作ユーザーが対象グループの権限を持つこと
- 参加月より前の履歴を閲覧できないこと

SQLiteの `CHECK` 制約だけでは複数行の合計や他テーブルの状態を保証できないため、Workerの検証と、8章の競合制御で扱う。

## 7. 定期処理（Cron Triggers）

- Cronは1時間ごとに動かし、各グループの `timezone` で日付を判定する。処理はすべて冪等にする（同じ時刻に2回動いても結果が変わらない）。
- 月初の処理：脱退月が締められていない脱退の確定（5章）。実装は `worker/src/cron.ts` の `runScheduled`（確定の中身は `worker/src/membership.ts` で、月締め・脱退を選ぶ操作と共通）。
  - 対象は、`status = 'active'` で、`leave_requested_month` がグループの今月（グループのタイムゾーン）より前のメンバー。部分索引 `idx_group_members_leave_requested` で、脱退を選んだままのメンバーだけを読む（毎時、全グループを読まない）。
  - 1回の実行で確定するのは `MAX_GROUPS_PER_RUN`（20）グループまで。古い月のグループから。残りは次の回が引き受ける。APIは、脱退月が終わったメンバーを確定したものとして扱う（5章）ので、遅れても、利用者の見える挙動は変わらない。
  - グループごとの書き込みが競合した（`'version'`）ら、その回は何も変えずに、次の回に回す。想定外のエラーは、そのグループだけを失敗として数え、ほかのグループは続けて、最後に投げる（Cronの実行を失敗にする）。
  - 脱退月がすでに締められていれば、確定と同時に、送金が済んでいるメンバーは脱退済みになる。最後の1人の脱退は、確定と同時にグループを削除する。
- 固定費の自動登録は、固定費のAPIと一緒に足す（未実装）。
- 固定費の自動登録：
  - 対象：`start_month` 以降、`end_month` 以前（または未設定）、`paused_at` が無いテンプレート。
  - 予定の月（`scheduled_month`）の `day_of_month` に達したら、支出を作る。`day_of_month` がその月の日数より大きい（31日指定の4月、29〜31日指定の2月など）ときは、月末日に作る。支出の日付も月末日にする。
  - 登録先の月（`target_month`）は、予定の月が未締めならその月。早めに締められていれば、最も古い未締めの月（通常は翌月）。日付は予定日のまま。この場合、翌月には翌月分の支出も作られ、2件になる。
  - 作るときは `recurring_expense_runs` に `(recurring_expense_id, scheduled_month)` を入れる。主キーの一意制約で二重作成を防ぐ。作った支出をユーザーが消しても記録は残るので、作り直さない。`writeToGroup` の失敗は、次のように扱う（8章）。
    - `'unique'`: `recurring_expense_runs` に同じ `(recurring_expense_id, scheduled_month)` の行があることを**読んで確かめたうえで**、作成済みとして正常に扱う。行が無ければ、別の原因（後続のSQLへの `GROUP_WRITE_GUARD` の付け忘れなど、実装の誤り）なので、正常にせずエラーとして記録する。`'unique'` は、どの制約に違反したかを区別せず、メッセージの形にも頼れないため、そのまま「作成済み」と決めつけると、固定費が作られないまま気づけない。
    - `'version'`: その実行ではやり直さず、次の時間のCronに回す。Cronは1時間ごとで冪等なので問題なく、利用者の操作との競合が続いても、1回の実行が長引かない。
  - 支出の作成は、通常の支出登録と同じく `data_version` を上げる（8章）。
- テンプレートの変更は、まだ作っていない月の分から反映する。作成済みの支出は変更しない（当月分だけ直したいときは、作られた支出を編集する）。

## 8. 同時操作・トランザクション

D1には対話的トランザクションがなく、`batch()` 単位でのみアトミック。`batch()` は直列に実行され、途中のSQLエラーで全体がロールバックされる。ただし、UPDATEやINSERT ... SELECTの対象が0件だっただけでは失敗しない。

### `expense_groups.data_version` と `write_token`

グループ内のデータへの書き込み（支出・割合・費目・固定費・締め・精算・繰越・参加・脱退・招待の発行と取り消し・グループ設定）は、すべて同じ方式で競合を検出する。

1. Workerが現在の `data_version`（`v`）を読む。そのあとで、検証と計算に使うデータを読み、検証と計算を行う（**バージョンが先**。下の注意）。
2. リクエストごとに一意な `write_token`（UUID）を作る。
3. batchの最初のSQLで、バージョンを上げ、tokenを書く。

   ```sql
   UPDATE expense_groups SET data_version = data_version + 1, write_token = ?token
    WHERE id = ?group AND data_version = ?v;
   ```

4. 後続のSQLは、すべて「`expense_groups.write_token` がこのリクエストのtokenと一致する」ことを条件にする。INSERTは `INSERT ... SELECT ... WHERE EXISTS (...)` の形、UPDATE・DELETEは `AND EXISTS (...)` を付ける。

   ```sql
   INSERT INTO expenses (...)
   SELECT ?, ?, ...
    WHERE EXISTS (SELECT 1 FROM expense_groups WHERE id = ?group AND write_token = ?token);
   ```

5. 最初のUPDATEの `meta.changes` が0なら、他のリクエストが先に書き込んでいる。このとき後続のSQLも条件を満たさず、何も変更されていない。

**注意：** 後続の条件を「`data_version = v + 1`」にしてはいけない。同じ `v` を読んだ別のリクエストが先に確定すると、バージョンは `v + 1` になっているため、0件だったはずの後続SQLが実行されてしまう。

**注意（読む順序）：** バージョンは、計算に使うデータより**先に**読む。データを先に読み、あとでバージョンを読むと、その間に入った別の書き込みの新しいバージョンと、古いデータを組み合わせてしまう。楽観ロックは通るので、別のリクエストの更新を黙って上書きする（lost update）。バージョンを先に読めば、間に入った書き込みはバージョンの不一致として検出される。検証用のデータの読み取りを増やすときも、この順序を崩さない。

実装は `worker/src/groupWrite.ts` の `writeToGroup`（後続SQLの条件は `GROUP_WRITE_GUARD`）。1つのグループへの書き込みは、必ずこれを通す（複数のグループにまたがるアカウント削除は、下の `writeToGroups`）。行数が多い書き込み（月締め）は、同じ条件つきで複数行を1文にまとめる `insertRowsGuarded` を使う（D1は batch の1文を1クエリと数え、Freeは1回の呼び出しにつき50までのため。1文に束縛できる値は100まで）。検査は `worker/test/groupWrite.test.ts`（ローカルD1）で、次を確かめてある。

- 古いバージョンで書くと、後続のINSERT・UPDATE・DELETEは何も変更しない。同じバージョンを読んだ複数のリクエストが書くと、成功するのは1つだけ。
- 「`data_version = v + 1`」の簡略形では、負けた側の後続SQLまで実行される（上の注意の実例。テストに入っている）。
- バージョンを後に読む順序では、別のリクエストの更新が上書きされる（上の注意の実例。テストに入っている）。
- 失敗の理由は2種類に分けて返す。呼び出し側の扱いが違うため（下の「競合したとき」）。
  - `'version'`: 最初のUPDATEが0件。他のリクエストが先に書いた。グループが存在しない場合も、ここに来る（404にしたいAPIは、先にグループを読んで確かめる）。
  - `'unique'`: 一意制約違反（`UNIQUE constraint failed`）。batch全体（バージョンの更新も含む）がロールバックされる。バージョンが合っていたときだけ後続のSQLが実行されるので、この違反は読み直しても同じ結果になる。
- CHECK・外部キー違反は実装の誤りなので、競合にせず例外のまま投げる。
- **ローカルD1で確かめたのはロジックまで。** ローカルD1（miniflare）は `batch` を直列に実行するので、並行して走ったときの性質は確かめていない。一意制約違反の判定がメッセージ文字列頼みであることも含め、本番D1での確認は公開前に行う（13章の9）。ローカルD1のエラーは `D1_ERROR: UNIQUE constraint failed: ...` で、元のメッセージが `cause` にも入る。判定は `cause` もたどる。

#### 複数のグループにまたがる書き込み（`writeToGroups`）

アカウント削除のように、複数のグループを1回の `batch()` で書くときの方式（実装は `worker/src/groupWrite.ts`）。

- バージョンを上げる文は、**1文**の UPDATE。全グループの `data_version` が読んだとおりのときだけ、全グループのバージョンを上げて、同じ `write_token` を書く。1つでも合わなければ、どのグループも変えない（グループごとに別々のUPDATEにすると、一部だけ書き込めた状態が残る。`worker/test/writeToGroups.test.ts` に実例）。
- 後続のSQLは、自分のグループの `GROUP_WRITE_GUARD` で足りる。token を書くのは、この1文だけで、全グループか、どのグループにもか、のどちらかになるため。
- グループ・バージョンは、`json_each` の1つの束縛で渡す（1文に束縛できる値は100まで。グループの数に制限されない）。
- バージョンを上げる文に、追加の条件を足せる。アカウント削除は、「読んだあとに、新しいグループのメンバーになっていない」をここで確かめる（「どのグループのメンバーか」は、バージョンより前に読むしかないため）。外すと、処理の途中で別のグループに参加された本人が、匿名化されずに残る（テストに入っている）。
- `expense_groups` の行を消す文は、ほかの文の最後にまとめる（先に消すと、そのグループの token の条件で、後続の文が効かなくなる）。
- ローカルD1では、1文のUPDATEで全グループが上がること、`json_each` の条件が通ることまでを確かめた。並行して走ったときの性質は、本番D1で確認する（13章の9）。

### 競合したとき

- 支出の登録・編集・削除、割合の変更、招待の発行・取り消しなど：Worker内で読み直して、1回だけやり直す。それでも競合したら409。`worker/src/groupWrite.ts` の `writeToGroupWithRetry` を使う。試行ごとにバージョンを読み、そのあとで、渡した `plan` が検証用のデータを読む。**検証用のデータの読み込みは、`plan` の中だけで行う**（外で読むと、バージョンより前に読むことになる）。
- 月締め・精算・繰越・参加・脱退を選ぶ・取り消す：やり直さず409を返し、アプリに最新の状態を読み直してもらう（確認ダイアログの内容が変わりうるため）。
- アカウント削除（`deleteAccount`）：読み直して数回（3回）までやり直す。それでも競合したら、何も変えずに失敗を返し、もう一度呼べる。
- バージョンの競合（`'version'`）だけが、やり直しの対象。一意制約違反（`'unique'`）は読み直しても同じ結果なので、やり直さない。業務上の扱いは呼び出し側が決める。
  - API：二重締め、すでに参加している、など。409を返す。
  - Cronの固定費の自動登録：`'unique'` は、作成済みであることを確かめたうえで正常として次へ進む。`'version'` は、その実行ではやり直さず、次の時間のCronに回す（7章）。

### 支出の対象月

- 支出は、登録する月（`target_month`）と日付（`expense_date`）を別に持ち、両者の関係は制限しない。入力漏れの書き方は利用者に任せる（内容に「先月分の○○」と書く、日付を月初にする、実際の日付のままにする、など）。
- 登録できる月は、未締めの月のうちカレンダー上の今月以前のもの。今月がすでに締められていれば、翌月。締めは古い月から順に行うので、未締めの月は連続している。通常は「今月（と、未締めなら前月）」、今月を早めに締めた後は「翌月」だけになる。
  - 下端は、最後に締めた月の翌月。まだ締めていなければ、グループを作った月（グループのタイムゾーン）。それより前の月に登録できると、未締めの月が連続しなくなるため。新しいメンバーは、これに加えて、参加（復帰）した月より前には登録できない（5章）。
  - 上端は、今月（グループのタイムゾーン）。下端のほうが新しければ（今月を締めた後）、下端と同じ。
  - 実装は `worker/src/months.ts` の `registerableRange`。
- アプリは、表示中の月を登録先にする。日付の既定値は今日。
- `target_month` が登録できる月であることは、Workerが読んだ時点で確認する。月締めもバージョンを上げるので、確認後に締められた場合は競合として検出される。やり直した検証で、その月は「登録できない月」として断られる（409 `month_not_registerable`）。
- 支出の支払者・負担の対象にできるメンバーは、その月に使えるメンバー（`worker/src/expenses.ts` の `isMemberAvailable`）。`deleted`・`left` は選べない。`active`・`leaving` は、参加（復帰）した月（`history_from_month`）から、脱退月までの月に選べる。脱退月は、脱退が確定していれば `expense_end_month`、脱退を選んだだけ（Cronの確定前）なら `leave_requested_month`（5章）。脱退月まで選べるのは、脱退が翌月1日のCronで確定した場合に、まだ締めていない脱退月の支出を、脱退者の支払として登録できるようにするため。

#### 招待・参加・脱退API（実装済み）

実装は `worker/src/invites.ts`（招待・参加）と `worker/src/leave.ts`（脱退を選ぶ・取り消す）。認証・エラーの形・月の形式は、支出APIの「共通」と同じ。グループを作るAPI（`POST /groups` など）は、まだ無い（12章）。

| API | 本文 | 成功 |
|---|---|---|
| `POST /groups/:id/invites` | なし | 201 `{ invite: { id, token, expiresAt, createdAt } }`。`token`（平文）は、この応答でだけ返す |
| `GET /groups/:id/invites` | なし | 200 `{ invites: [{ id, expiresAt, createdAt }] }`（自分が発行した、未使用で期限内のもの） |
| `DELETE /invites/:id` | なし | 204（発行した人だけ。すでに取り消し済みでも204） |
| `GET /invites/:token` | なし | 200 `{ alreadyMember: false, groupName, invitedByDisplayName, expiresAt }`。すでに参加中なら 200 `{ alreadyMember: true, groupId }` |
| `POST /invites/:token/join` | `{ "displayName": "…" }` | 201 `{ groupId, memberId }` |
| `POST /groups/:id/leave` | なし | 200 `{ leaveRequestedMonth, confirmed }`。最後の1人の脱退が確定したときは、`groupDeleted: true` も付く |
| `DELETE /groups/:id/leave` | なし | 200 `{ leaveRequestedMonth: null }` |

- 招待トークンは、256ビットの乱数（base64url の43字）。D1にはSHA-256のハッシュだけを置く。期限は発行から3日、使い捨て。`/invites/:x` は、GET が招待トークン、DELETE が招待のID。形が違えば404。
- 発行できるのは、脱退が確定していない参加中のメンバー（`leaving` 以降と、脱退月が終わったメンバーは403）。1人が持てる、未使用で期限内の招待は10件まで（409 `too_many_invites`）。
- 確認（GET）は、URLを開いただけでは何も変えない。使えない招待（知らないトークン・期限切れ・使用済み・取り消し済み・発行者が抜けた）は、理由を区別せず404 `invite_unavailable`。すでにそのグループに参加中なら、招待の状態によらず `alreadyMember: true`。
- 参加（POST）: 表示名は必須（前後の空白を落として1〜20文字。コードポイントで数える）。色はサーバーが選ぶ（他の参加中のメンバーと重ならない最初の色。全色が使われていれば、使われている数で一巡する）。色のキーは、仮の一覧 `pink, red, orange, yellow, green, teal, blue, purple, brown, gray`（`worker/src/membership.ts` の `MEMBER_COLORS`。アプリの色の一覧と揃える）。参加の中身は5章。
- 参加・脱退を選ぶ・取り消すは、やり直さずに409 `conflict`（同じ招待で同時に参加すると、片方だけが参加し、もう片方は409）。招待の発行・取り消しは、読み直して1回だけやり直す（8章）。
- 脱退を選ぶ: `leaveRequestedMonth` は、グループのタイムゾーンの今月。脱退月がすでに締められていれば、その場で確定する（`confirmed: true`。5章）。
- 脱退の取り消しは、確定するまで。脱退月が終わったあとは、Cronの確定の前でも取り消せない（409 `leave_confirmed`）。

| 状態 | `error` | 意味 |
|---|---|---|
| 401 | `unauthorized` | セッションが無い・無効・期限切れ |
| 403 | `forbidden` | 招待の発行：脱退が確定した（確定したものとして扱う）メンバー |
| 404 | `not_found` | グループ・招待が無い、メンバーでない、脱退済み・削除済み、発行した人でない（取り消し）。区別しない |
| 404 | `invite_unavailable` | 招待の確認・参加：使えない招待 |
| 409 | `already_member` | 参加：すでに参加中。`{ groupId }` を添える |
| 409 | `too_many_invites` | 招待の発行：未使用の招待が上限 |
| 409 | `invite_already_used` | 招待の取り消し：すでに使われている |
| 409 | `leave_already_requested` | 脱退を選ぶ：すでに選んでいる |
| 409 | `leave_confirmed` | 脱退を選ぶ・取り消す：すでに確定した（脱退月が終わったものを含む） |
| 409 | `not_leaving` | 脱退の取り消し：選んでいない |
| 409 | `conflict` | 他のリクエストの書き込みと競合した（8章） |

#### 支出API（実装済み）

実装は `worker/src/expenses.ts`（入力の検査は `worker/src/expenseInput.ts`、権限の判定は `worker/src/access.ts`）。アプリとは、コードを共有せず、この節を正として両側に書く。

共通：

- 認証は `Authorization: Bearer <セッションの値>`。本文・応答はJSON。HTTPSでないリクエストは403。
- ID（グループ・支出・費目・メンバー）は、英数字・`-`・`_` の64字まで。形が違うパス、知らないパスは、JSONの404 `{ "error": "not_found" }`。
- 知らない項目、型や範囲の違う値は400 `{ "error": "invalid_request", "field": "<直す項目>" }`（`split.shares` のように、入れ子は `.` でつなぐ。値は返さない）。空の本文など、項目を特定できないときは `field` を付けない。本文の上限は16KB（超えたら413）。
- 金額は通貨の最小単位の整数（`amountMinor`、1〜10^12）。割合は1万分率の整数（`basisPoints`）。
- 月は `YYYY-MM`、日付は `YYYY-MM-DD`（実在する日付）。内容（`description`）は任意で、前後の空白を落とし、空なら `null`。100文字まで（コードポイントで数える）。

支出（`Expense`）：

```json
{
  "id": "…", "expenseDate": "2026-11-19", "targetMonth": "2026-11",
  "description": "スーパー", "amountMinor": 4280,
  "categoryId": "…", "payerMemberId": "…", "createdByMemberId": "…",
  "recurringExpenseId": null,
  "splitMethod": "category",
  "allocations": [{ "memberId": "…", "burdenMinor": 500, "shareBasisPoints": null }],
  "createdAt": 1790000000000, "updatedAt": 1790000000000
}
```

`allocations` は、`category` 以外の支出の確定負担額（メンバーのID順）。`category` では `[]`（月の集計で計算する。3章）。`shareBasisPoints` は割合指定（`ratio`）のときだけ入る。

| API | 本文・クエリ | 成功 |
|---|---|---|
| `GET /groups/:id/expenses?month=YYYY-MM` | `month` は必須 | 200 `{ month, closed, expenses: [Expense] }`。日付の新しい順（同じ日付は登録の新しい順）。`closed` は、その月が締め済みか |
| `POST /groups/:id/expenses` | `expenseDate`・`targetMonth`・`amountMinor`・`categoryId`・`payerMemberId`・`split` が必須、`description` は任意 | 201 `{ expense }` |
| `PATCH /expenses/:id` | 登録と同じ項目のうち、変えるものだけ（1つ以上）。`description` は `null` で消す | 200 `{ expense }` |
| `DELETE /expenses/:id` | なし | 204 |

負担の指定（`split`）：

| `method` | 項目 | 備考 |
|---|---|---|
| `category` | なし | 費目の割合で分ける（既定） |
| `equal` | `memberIds`（1人以上、重複なし） | 均等割り。端数は固定順（2章） |
| `ratio` | `shares: [{ memberId, basisPoints }]` | 合計10000。0%のメンバーも入れられる（端数は配らない） |
| `fixed` | `amounts: [{ memberId, amountMinor }]` | 合計が `amountMinor` と一致（違えば400 `split.amounts`） |
| `single` | `memberId` | 1人が全額負担 |

編集の規則：

- 送らなかった項目は変えない。`split` を送ると、負担額を丸ごと置き換える（`category` に戻すと負担額を消す）。
- **`category` 以外の支出の金額を変えるときは、`split` も送る**（無ければ400 `split`）。画面で確認した負担を、サーバーが勝手に計算し直さないため。金額を変えずに内容や日付だけ直すときは、保存した負担額をそのまま残す。
- 支払者・負担の対象は、その月に使えるかを、**新しく選んだメンバー（支払者を変えた、負担の指定に加えた）と、負担額が増えるメンバー**について検証する。脱退・削除したメンバーが入った既存の支出でも、内容や日付は直せる。負担の指定ごと送り直しても、その人の負担額が増えなければ通る。「増える」は、保存した負担額（金額）と比べる。そのため、割合を上げても、金額を下げて負担額が増えなければ通る。逆に、削除したユーザーを含む均等割り・割合割りは、金額を上げると全員の負担額が増えるので断られる（金額指定に切り替えれば、そのメンバーの負担額をそのままにして上げられる。画面の案内は screens.md 4章）。一方、本人が異議を出せない相手（削除したユーザーなど）に、負担を寄せ直すことはできない。`targetMonth` を変えるときは、全員分見直す。グループに居るかは、どのメンバーも必ず見る。
- アーカイブした費目の支出は、費目を変えないかぎり、編集できる（別の月に移すことも含む。アーカイブの判定は、費目を選ぶときだけ）。
- 登録する月を変えるときは、移し先が登録できる月（8章）であること。
- 締め済みの月の支出は、編集も削除もできない（409 `month_closed`）。

エラー：

| 状態 | `error` | 意味 |
|---|---|---|
| 401 | `unauthorized` | セッションが無い・無効・期限切れ |
| 403 | `forbidden` | 脱退が確定したメンバー（`leaving`）、または脱退月が終わったメンバー（5章）の書き込み。参加前の月の一覧 |
| 404 | `not_found` | グループ・支出が無い、メンバーでない、脱退済み・削除済み、他のグループのID、参加前の月の支出。区別しない（IDの存在を教えない） |
| 409 | `month_not_registerable` | 登録先の月が登録できない（締め済み、先すぎる、作成前、参加前）。`{ from, to }` に登録できる範囲を添える |
| 409 | `month_closed` | 編集・削除の対象が締め済みの月 |
| 409 | `member_not_available` | 支払者・負担の対象が、その月に使えない。`{ memberId }` を添える |
| 409 | `category_not_available` | アーカイブした費目 |
| 409 | `conflict` | 読み直してやり直しても、他のリクエストの書き込みと競合した（8章）。入力は残して、読み直してもらう |

他のグループの費目・メンバーのIDを指定したときは、404でなく400。`field` は、費目なら `categoryId`、支払者なら `payerMemberId`、負担の対象なら負担の方法に合わせた項目（`split.memberId`・`split.memberIds`・`split.shares`・`split.amounts`）。

### 月締め・精算

#### 月締め・精算API（実装済み）

実装は `worker/src/closings.ts`（月次集計・月締め・締め結果）と `worker/src/transfers.ts`（精算・繰越）。集計の読み込みと計算は `worker/src/monthState.ts` の `loadMonthState` と `computeMonthFromState` にだけ置き、締める前の見込み（summary）と月締めで同じものを使う（締めた結果が、直前の見込みとずれないように）。アプリとは、コードを共有せず、この節を正として両側に書く。認証・エラーの形・金額と月の形式は、支出APIの「共通」と同じ。`:month` が `YYYY-MM` でなければ404。

| API | 本文 | 成功 |
|---|---|---|
| `GET /groups/:id/months/:month/summary` | なし | 200 `MonthView`。締める前の月は現在の支出から計算した見込み（前の月からの繰越を足す）、締めた月は締めた時点の結果 |
| `POST /groups/:id/months/:month/close` | なし | 201 `MonthView`（締めた結果。`close` は付かない） |
| `GET /groups/:id/months/:month/closing` | なし | 200 `MonthView`（締めた月だけ。`close` は付かない） |
| `POST /transfers/:id/settle` | なし | 200 `{ transfer }`（精算済みにする） |
| `POST /transfers/:id/carry` | なし | 200 `{ transfer }`（次の月に繰り越す） |

`MonthView`（締めた月）：

```json
{
  "month": "2026-10", "closed": true,
  "closing": { "id": "…", "closedAt": 1790000000000, "closedByMemberId": "…", "processed": false },
  "totalMinor": 14000,
  "members": [{ "memberId": "…", "displayName": "…", "paidMinor": 10000, "burdenMinor": 7000,
                "differenceMinor": 3000, "carriedInMinor": 0, "netMinor": 3000 }],
  "categories": [{ "categoryId": "…", "totalMinor": 14000,
                   "burdens": [{ "memberId": "…", "burdenMinor": 7000 }] }],
  "transfers": [{ "id": "…", "fromMemberId": "…", "toMemberId": "…", "amountMinor": 3000,
                  "status": "pending", "settledAt": null, "carriedAt": null,
                  "processedByMemberId": null, "canCarry": true }],
  "close": { "closable": false, "reason": "month_closed" }
}
```

- `totalMinor` はその月の支出の総額で、繰越を含めない。`members[].burdenMinor` と `categories` の負担額にも繰越は入らない。繰越は `carriedInMinor`（送金先なら足し、送金元なら引く）と `netMinor`（精算する額 = 差額 + 繰越）にだけ入る（3章・4章）。
- `members` は固定のメンバー順（IDの昇順）。その月に参加している全員（参加月から脱退月まで。削除したユーザーも、削除した月まで）と、支出・費目の割合・繰越に出てくる全員が並ぶ。支出に関わらなくても0で出る。`displayName` は、締めた月では締めた時点の名前。
- `categories` は、支出がある費目だけ（`categoryId` の昇順）。`totalMinor` は個別設定の支出を含む合計、`burdens` は費目の割合による分と個別設定の分の合計で、負担額が0のメンバーの行は無いことがある。
- 締める前の月（`closed: false`）は、`closing` が `null`、`transfers` が見込み（`{ fromMemberId, toMemberId, amountMinor }` だけ。IDも状態も無い。締めるまで確定しない）。締めた月の `transfers` は、送金ごとに状態つき。
- `processed`：すべての送金が `settled` か `carried`（送金が0件の月も true。4章）。
- `canCarry`：未処理で、送金元・送金先がどちらも繰り越せるメンバー（`active` で `leave_requested_month` なし）のときだけ true。アプリが規則を持たなくて済むように返す。
- `close`（summary だけ）：その月を、いま操作しているメンバーが締められるか。締められれば `{ "closable": true }`、締められなければ `{ "closable": false, "reason": "…" }`。`reason` は、月締めの409・403のエラー名と同じ（下の表）で、`previous_month_not_closed`・`previous_month_unsettled` には `month`（先に済ませる月）が付く。まだ締められない月の見込みも、同じ形で返す（アプリが「先に10月を締めてください」を出せるように）。
- まだ始まっていない月も、summary は返す（集計は空に近く、`close.reason` は `month_not_started`）。
- 締めずに飛ばした月（最後に締めた月より前で、締めていない月）の summary は、`closed: false` のまま、`close.reason` が `month_skipped`。「締め済み」ではないので、アプリは `month_closed` と同じ表示にしない。

月締めの書き込み（4章）は、1回の `writeToGroup`（8章）。この月を脱退月に選んでいるメンバーの脱退は、この書き込みの中で確定する（5章）。そのメンバーが最後の1人のときは、締めずにグループを削除し、200 `{ "groupDeleted": true }` を返す。**やり直さず**、競合したら409 `conflict`（確認ダイアログの内容が変わりうるため。アプリは読み直して案内する）。二重締めの同時実行は、片方だけが締まり、もう片方は409 `conflict`（すでに締められたあとなら `month_closed`）。D1のクエリ数は、読み込みが約16（認証・バージョン・権限・状態10・結果5。数は固定）と、書き込みの文の数。書き込みは複数行を1文にまとめている（束縛できる値は1文に100まで。1文に入る行数は、費目の設定・割合が19行、費目ごとの負担が16行、メンバーごとの集計が10行まで）ので、行数に比例して増えず、費目×メンバーの数に応じてゆるやかに増える。小さなグループで実測約25（認証を含む）、費目13・メンバー3で、書き込みは12文（`worker/test/closings.test.ts` の「D1のクエリ数」）。費目30・メンバー6あたりで、Freeの上限（1回の呼び出しにつき50）に近づく。公開時に移行するWorkers Paid（上限は1回につき1000）では問題にならない。

精算・繰越（4章）：

- 状態は `pending → settled`、`pending → carried` だけ。確定後に戻せない（409 `transfer_not_pending`、`status` に今の状態を添える）。`UPDATE` にも `AND status = 'pending'` を付けている。
- 全メンバー（`active`・`leaving`）が、当事者でない送金も操作できる。ただし、送金のある月を見られるメンバー（参加前の月の送金は404）。
- 繰越は、送金元・送金先に、脱退を選んだ（`leave_requested_month` あり）・`leaving`・`left`・`deleted` のメンバーがいると、409 `transfer_not_carryable`。精算済みにはできる。
- 精算済みにした結果、脱退が確定した（`leaving`）メンバーの未処理の送金が無くなり、脱退月が締められていて、繰越先の月が未締めの繰越も無ければ、そのメンバーを `left` にする（5章の4。同じ `batch` の中）。
- 精算・繰越も、やり直さずに409 `conflict`。応答の `transfer` は、更新後の送金（`canCarry` は false）。

エラー：

| 状態 | `error` | 意味 |
|---|---|---|
| 401 | `unauthorized` | セッションが無い・無効・期限切れ |
| 403 | `forbidden` | 参加前の月の summary・closing。月締めで、操作者がその月のメンバーでない（参加前の月、脱退月が終わった月） |
| 404 | `not_found` | グループ・送金が無い、メンバーでない、脱退済み・削除済み、他のグループのID、参加前の月の送金。区別しない（IDの存在を教えない） |
| 404 | `not_closed` | closing：まだ締めていない月 |
| 409 | `month_not_started` | 月締め：まだ始まっていない月（グループのタイムゾーンで、今月より後） |
| 409 | `month_closed` | 月締め：すでに締められている |
| 409 | `month_skipped` | 月締め：最後に締めた月より前で、締めていない月（飛ばした月。4章） |
| 409 | `previous_month_not_closed` | 月締め：前の月が未締め。`{ month }` に先に締める月を添える |
| 409 | `previous_month_unsettled` | 月締め：前の月の送金に未処理が残っている。`{ month }` を添える |
| 409 | `transfer_not_pending` | 精算・繰越：すでに処理済み。`{ status }` を添える |
| 409 | `transfer_not_carryable` | 繰越：脱退予定・削除したユーザーなどが関わる送金 |
| 409 | `conflict` | 他のリクエストの書き込みと競合した（8章）。読み直してもらう |

費目の設定が無い費目の `category` の支出が月にあると、集計できずに500になる（費目を作るときに、必ず月の設定と割合を書く。付録A-7）。

全APIで、認証・グループ所属・対象データのグループ一致・月の閲覧範囲・締め状態をWorker側で検証する。IDを知っているだけで他グループのデータにアクセスできないようにする。これらの判定は共通の関数にまとめる。Premiumの閲覧期間の制限（企画メモ10章）を導入するときも、同じ関数に足す。

## 11. 必須テスト

### 金額・負担計算

- JPY・USD・小数桁3の通貨での金額保存と表示
- 2人・3人以上の均等割り
- 割合合計10000の正常ケース、10000でないケースの拒否
- 金額指定の合計一致・不一致
- 端数が出る場合の固定順配分（割合0%のメンバーには配らない）
- 支払者と負担者が異なるケース
- 費目の月合計 × 割合で計算されること（企画メモ5章の精算例が、相手から自分へ17,000円になる）
- 上限額つきの負担：月合計が上限以下・ちょうど上限・上限超えの3通り。超えた分の割合を、負担する人0%・0%以外の両方で
- 月の途中で割合を変えると、その月の `category` の支出すべてに反映されること
- 個別設定の支出が、費目の合計から除外されること
- 割合の行が無い月が、直前の月の割合を引き継ぐこと
- 全員の差額の合計がゼロになること

### 月締め

- 通常の月締め
- 月の途中での締め、まだ始まっていない月の締めの拒否
- 前の月が未締め、または未処理の送金がある状態での締めの拒否
- 同じ月の二重締め
- 締め後の支出追加・編集・削除、割合変更の拒否
- 月締め中に支出登録・割合変更が競合（同じ `data_version` を読んだ2リクエストで、片方の後続SQLが実行されないこと）
- 3人以上の精算組み合わせ
- 精算済み・繰越・未処理の混在
- `settled`・`carried` から別の状態への変更の拒否
- 脱退予定・脱退処理中のメンバーが関わる送金の繰越の拒否
- 繰越が、翌月の支出の総額・負担額には加算されず、翌月の締めの精算する額に加算されること
- 2か月続けて繰り越したときに、金額を二重に数えないこと
- 3人で繰越がある月の送金の合計が、メンバーごとの精算する額と一致すること
- 早めに締めた後、同じ暦月の日付の支出を翌月分として登録できること
- 登録できる月以外（締め済みの月、2か月以上先の月）への登録の拒否

### メンバー・権限

- 招待URLを開いただけでは参加しない
- 期限切れ・使用済み・取消済み招待の拒否
- 同じ招待での同時参加で、1人だけ参加できること
- 発行者の脱退確定・アカウント削除で、未使用の招待が取り消されること
- 参加月の割合が均等にリセットされ、上限額の設定が外れること、個別負担の固定費が止まること
- 異なるグループのIDを指定した操作の拒否
- 参加月より前の履歴閲覧拒否
- 脱退の取り消し（当月中）と、翌月以降の取り消しの拒否
- 脱退月が終わったあと、Cronが確定させる前でも、本人が支出を記録できず、他のメンバーが本人を翌月以降の支払者・負担の対象にできないこと
- 脱退確定後、送金がすべて精算されるまで `leaving` のままであること
- 脱退後も過去の精算参照が壊れないこと、名前が残ること
- 再参加で元のメンバー行に戻り、履歴が復帰月以降になること
- 脱退月を早めに締めた時点で脱退が確定し、取り消せなくなること
- 早めに締めた後に脱退を選ぶと、その場で確定すること
- 最後の1人の脱退でグループのデータがすべて消えること
- アカウント削除時の名前匿名化（過去に脱退したグループを含む）
- 削除したユーザーが、削除した月までの集計に含まれ、翌月の割合から外れること
- 削除したユーザーが関わる送金を繰り越せず、精算済みにはできること
- アカウント削除後に認証情報から本人を再特定できないこと

### 固定費

- 同じ月に同じ固定費が二重生成されないこと
- 生成された支出を消しても、同じ月に作り直されないこと
- 生成済み支出がテンプレート変更で変化しないこと
- 31日指定など、月末に存在しない日付の扱い
- 停止中・終了後のテンプレートから新しい支出が生成されないこと
- 予定の月が早めに締められていたら、最も古い未締めの月に登録されること

## 12. 実装前に残る確認事項

- **アカウント削除のAPI（`POST /auth/delete`）が無い。** データの匿名化・削除は、`worker/src/accountDeletion.ts` の `deleteAccount` に実装した（複数グループの競合制御は、8章の `writeToGroups`で決めた）。セッション・再認証・Appleのrevokeを確かめたあとで、これを呼ぶ。1回の `batch()` の文の数は、関わるグループの数に比例して増える（Freeは1回の呼び出しにつき50まで）ので、公開時のPaid移行（13章の9）の前に、グループが多い人で数を確かめる。
- **お知らせ（アラート）の覚え方。** メンバーの増減で割合を均等に戻したこと、固定費が止まったこと、脱退する人が支払者の固定費の付け替えを、ホームに出す（screens.md 2章）。サーバーは、割合のリセットと固定費の停止（`paused_reason`）までは書くが、「メンバーが変わったため、割合を戻した」ことを覚える場所が無い。案：メンバーが変わった月を持つ列を足す、または月ごとの「見直し済み」の印を持つ。割合を直すAPIと一緒に決める。
- **全員が脱退済みになったグループの後片付け。** 最後の1人の脱退は、確定のときにグループを消す（5章）。2人以上が同時に抜けて、精算を済ませて全員が `left` になったグループは、誰も見られないまま残る。案：月初のCronで、参加中・脱退が確定したメンバーがいないグループを消す。
- **グループのメンバー数の上限。** 決めていない。月の集計・月締めは、メンバー数に応じて重くなる（D1のクエリ数・CPU時間）。
- **グループ・費目・固定費のAPIが、13章の順に無い。** `POST /groups`（作成）、`GET /groups`・`GET /groups/:id`・`PATCH /groups/:id`、費目・負担割合・固定費（9章）、メンバーの名前・色の変更。テストは、グループ・メンバー・費目をSQLで用意している。固定費の自動登録のCron（7章）は、固定費のAPIと一緒に足す。

- **支出の二重送信。** 通信が途切れてアプリが同じ登録を再送すると、支出が2件できる。Workerの内部のやり直し（8章）は、書き込みが取り消されたあとなので安全。アプリが作るID（冪等キー）を受け取って、同じIDの再送を同じ結果として返す案がある。13章の8（二重登録の統合テスト）の前に決める。
- **ログイン・ログアウトのAPIが13章の順に無い。** 支出のAPIのために、認証のうちセッションの確認（`worker/src/session.ts` の `authenticateSession`）だけをSingfolioからコピーした。ログイン（`/auth/nonce`・`/auth/login`・AndroidのApple）、ログアウト、アカウント削除は未実装。アプリから呼べるようにするまでに、同じ元から取り込む。

- **ホームの月ピッカーの状態の印（未締め / 精算が残っている / 処理済み。screens.md 2章）を返すAPIが無い。** 9章の月締め・精算APIは1か月ずつ。グループ・メンバーのAPI（9章）を決めるときに、月の一覧（月ごとの締め・未処理の送金の有無）を返すAPIを足す。

（以前の確認事項は、固定費の月末日を7章、匿名化の範囲を5章、対応通貨を2章で決めた）

   - 8章の競合制御が、並行して走るリクエストでも、成功を1つに絞ること。
   - 複数行INSERT（`insertRowsGuarded`、`VALUES` を副問い合わせにした `INSERT ... SELECT`）が、本番D1でも通ること。1文に束縛できる値は100までとして分けている。
   - 月締めのD1クエリ数（小さなグループで実測約25。ローカルD1での数。費目×メンバーの数で増える。9章）が、Freeの上限（1回の呼び出しにつき50）に収まること。
   - 一意制約違反のエラーの形が、`isUniqueViolation`（`worker/src/groupWrite.ts`）の判定に合うこと。外れると、`'unique'` が例外（500）に変わる。
   - 複数グループの書き込み（`writeToGroups`。全グループを上げる1文のUPDATEと、`json_each` の束縛）が、本番D1でも通ること。
   - 月初のCronの部分索引（`idx_group_members_leave_requested`）が、本番D1でも効くこと（`EXPLAIN QUERY PLAN`）。

**この文書は設計方針のまとめであり、SQLはまだ本番投入用の確定版ではない。** 次工程では、実際のマイグレーションを作りながらSQLite/D1で制約とトランザクションを検証する。

# 付録A：D1用SQL DDL 初版

> 注意：以下のDDLは `worker/migrations/0001`〜`0006` に分けて置いてある（10章）。ローカルのD1で適用と主な制約は確かめたが、トランザクション、削除・匿名化の挙動は、APIを作るときに確かめる。

共通の約束（Singfolioに揃える）：

- テーブルは `STRICT, WITHOUT ROWID`。IDはTEXT（UUID）。
- 日時はUnixエポックのミリ秒（INTEGER）。月は `YYYY-MM`、日付は `YYYY-MM-DD` のTEXT。
- D1は外部キーを既定で強制するので、`PRAGMA foreign_keys` は書かない。
- 金額の上限 `1000000000000`（2章）は、実装時に定数として1か所にまとめる。
- グループの配下のテーブルには、すべて `group_id`（またはその親のID）が先頭にくる主キーか索引を持たせる。理由は2つ。
  - グループの削除は `group_id` で行を消すので、索引が無いと、全グループの行を読むことになる。D1は読んだ行数で課金される。
  - 親の行（メンバー・費目など）を消すとき、SQLiteは子のテーブルを外部キーの列で探す。子の側に、外部キーのどれかの列が先頭にくる索引が無いと、子のテーブル全体を読む。複合外部キーは `(xxx_id, group_id)` なので、`group_id` が先頭の索引があれば、そのグループの行だけを読めば済む。
- 自由入力の文字数の上限は、DDLのCHECKにも置く（APIでも検証する）。グループ名30文字、表示名20文字、費目名20文字、支出・固定費の内容100文字。

  FOREIGN KEY (member_id, group_id) REFERENCES group_members (id, group_id)

CREATE TABLE settlement_transfers (
  id TEXT PRIMARY KEY NOT NULL,
  group_id TEXT NOT NULL,
  closing_id TEXT NOT NULL,
  from_member_id TEXT NOT NULL,
  to_member_id TEXT NOT NULL,
  amount_minor INTEGER NOT NULL CHECK (amount_minor > 0),

  FOREIGN KEY (from_member_id, group_id) REFERENCES group_members (id, group_id),

CREATE INDEX idx_settlement_transfers_group ON settlement_transfers (group_id, closing_id);

## A-7. DDLだけでは保証できないこと

以下は複数行・複数テーブルにまたがるため、Worker側の検証と8章の競合制御で保証する。

- `category_month_shares` の、1つの費目・月の割合合計が10000であること。
- `category_month_settings` と `category_month_shares` が同じ月でまとめて書かれること。上限額を負担する人が、その月の `category_month_shares` に含まれること。
- `expense_allocations.burden_minor` の合計が支出総額と一致すること。`category` の支出に行が無いこと。
- 金額指定の各 `amount_minor` の合計が支出総額と一致すること。
- 支払者・負担者が、支出の対象月に有効なメンバーであること。
- 月締め後に、対象月の支出・負担割合を変更できないこと。
- 送金の状態が `pending` からしか変わらないこと（UPDATEに `AND status = 'pending'` を付ける）。
- グループ通貨が支出登録後に変更されないこと。
- 費目ごとの `closing_category_burdens.burden_minor` の合計が `total_minor` と一致すること。
- 匿名化時に `group_members.display_name` と `closing_member_summaries.display_name_snapshot` の両方を更新すること。
- `users` の削除前に、メンバー行の匿名化と `user_id` の解除を済ませること。
